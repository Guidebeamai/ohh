# Proposal: v0.3 — protected access, claim provenance and profile kinds

> **Status:** Draft, not yet open for comment
> **Author:** Adnan Lodhi, with Claude
> **Created:** 2026-10-29
> **Breaking:** yes. v0.2 harnesses need migrating (see [Migration](#migration-from-v02)).
> **Tracking:** Guidebeam Linear GUI-511 (build), GUI-512 (verifiable credentials, v0.4), GUI-513 (tooling)

## Summary

v0.3 fixes the hole at the centre of v0.2: a harness marks sections `permissioned` or `private`, then publishes them in a public file. In v0.3 the published file contains only public data. Everything else is served by a protected endpoint. A requester reaches it through OAuth, using the UMA 2.0 grant, because the requester is not the person whose data it is. v0.3 also records where every claim came from, and stops assuming every harness belongs to a freelancer.

## Why

### What's broken in v0.2

1. **Private data is public.** The harness is one file at `/.well-known/hiring-harness.json`. Its sections carry a `visibility` label, but the file is served to anyone, so the label protects nothing. In the v0.2 example, anyone can read the day rate (`permissioned`), the availability notes (`private`) and the endorsements (`permissioned`).
2. **The consent log is public too.** It lives at `/.well-known/hiring-consent-log.json` and is described as "private by default", which a well-known public path cannot be.
3. **Revocation can't happen.** The revocation endpoint is `harness://consent/revoke`, which no client can call.
4. **Requesters are trusted on their word.** `RequesterIdentity` is whatever the requester says it is. Nothing ties "Example Platform" to a real party.
5. **Every claim looks the same.** "Expert in Python" typed by the owner, an assessment score, and a client's endorsement all have the same standing.
6. **Only freelancers fit.** `offer.rates`, `offer.services`, `offer.roles` and `offer.specialties` are required, so a student, a job seeker or an employee cannot produce a valid harness.

### Why these three changes together

They are the minimum for OHH to be what it claims: a record the person controls and that others can trust. Protection without provenance gives you private claims nobody can weigh; provenance without protection publishes the evidence. Profile kinds are in the same release because they change which fields are required, and making the schema break twice in a row would cost more than doing it once.

## Goals

- Nothing in the published file is readable that the owner didn't choose to make public.
- A requester gets non-public data only with a grant that names who they are, what they want and why, and that the owner (or the owner's delegate, within the owner's rules) approved.
- Grants are time-limited and revocable, and revocation works through a real URL.
- Every claim says where it came from, and consumers can tell a self-declared claim from an attested one.
- A harness can describe a freelancer, a job seeker, an employee or a student.
- Skills and occupations can be matched across systems through standard codes.
- Someone who knows OAuth and JSON Schema can implement it from this document and the schema, without Guidebeam's software.

## Non-goals (v0.3)

- **Cryptographic verification of claims.** Attested claims in v0.3 say who attested them; proving it with Verifiable Credentials is v0.4 (GUI-512).
- **AI agents as hireable entities.** The [agent entities proposal](agent-entities.md) stays a separate proposal. v0.3 only adds the `entity_type` field with one value, `individual`, so agents can be added later without another breaking change.
- **A hosted service.** OHH stays a specification. Running a host is the implementer's job.
- **Identity verification of the owner.** v0.3 does not prove the person publishing a harness is who they say they are.

## Anti-goals (would make v0.3 a failure even if it validates)

- **Inventing a security protocol.** If v0.3 defines its own token, signature or handshake format instead of using OAuth and existing RFCs, it has failed.
- **A design only Guidebeam can implement.** See [GOVERNANCE.md](../../GOVERNANCE.md).
- **Exposing minors.** Any path by which a student's personal data ends up in a public file or a search index.
- **Ranking people.** Provenance describes evidence. It must not become a score or a star rating (README design principles).

## Design

### 1. Two surfaces: the published harness and the protected resource

A v0.3 harness has two surfaces.

| Surface | Where | Who can read it | Contains |
|---|---|---|---|
| **Published harness** | An HTTPS URL; see [Discovery](#discovery-one-person-per-url) | Anyone | Sections whose visibility is `public`, the policy blocks, and a pointer to the protected resource |
| **Protected resource** | An HTTPS URL per harness, declared in the published harness | Requesters holding a valid token for that harness | Sections whose visibility is `permissioned` or `private` |

**What counts as a section.** A section is anything wrapped in an envelope. v0.3 has these envelopes, each with its own scope (section 2):

| Section | v0.2 | v0.3 change |
|---|---|---|
| `identity` | plain object | **becomes an envelope**; `identity.contact` stays a separate envelope inside it |
| `identity.contact` | envelope | unchanged |
| `offer` | plain object | **becomes an envelope** covering roles, specialties, skills, services, industries and working preferences |
| `offer.rates` | envelope | unchanged |
| `availability.summary`, `availability.detail` | envelopes | unchanged |
| `proof` | envelope | unchanged |
| `reputation.redacted`, `reputation.full` | envelopes | unchanged |
| `career_fit` | — | new envelope (section 7) |

`profile`, `access`, `privacy`, `consent` and `requester_policy` are **policy blocks**, not sections. They are always public and always inline, because a requester needs them before it can ask for anything.

**The envelope changes.** In v0.2 every section is an envelope with `visibility` and `data`. In v0.3:

- a `public` envelope keeps `data` inline;
- a `permissioned` or `private` envelope **must not** contain `data`. It contains `href`, the URL of that section on the protected resource, and `scopes_required`.

The schema enforces this with an `if`/`then` on `visibility`, so a v0.3 harness that inlines non-public data fails validation. This rule is the core of the release and gets failing fixtures in `tests/invalid/`.

```json
"rates": {
  "visibility": "permissioned",
  "href": "https://harness.example.com/v0.3/sections/rates",
  "scopes_required": ["ohh:rates.read"]
}
```

**What `private` means now.** `permissioned` sections can be granted under the owner's standing rules (including by a delegate). `private` sections need the owner's explicit approval for each grant, as v0.2 intended. Both are served only from the protected resource.

**The protected resource returns the same shapes.** `GET {href}` with a valid token returns the envelope with `data` filled in, validated against the same `$defs` the schema already has (`RatesData`, `AvailabilityDetailData` and so on). The schema publishes a "resolved section" definition for each so implementers can validate both surfaces.

**Two schemas: published and resolved.** Rules that depend on non-public data can't be checked on the published file alone. The v0.3 schema therefore has two entry points:

- the **published harness schema**, which checks the public file, including that no non-public `data` is inline;
- the **resolved harness schema**, which checks the published file merged with every protected section. This is what the owner's host validates before publishing. Kind-specific requirements (section 5) are checked here.

<a id="discovery-one-person-per-url"></a>**Discovery: one person per URL.** v0.2 assumed one person per domain. v0.3 identifies a harness by its URL, so a host can serve many people:

- People with their own domain keep using `/.well-known/hiring-harness.json`. The DNS TXT record and `<link rel="hiring-harness">` from v0.2 still work and may now point at any HTTPS URL.
- Hosts serve one URL per person, for example `https://host.example/h/{handle}/hiring-harness.json`, and use `<link rel="hiring-harness">` on the person's profile page to point to it.
- A harness may have **no published file at all**. In that case it's reachable only by a requester the host already lets in. Students' harnesses default to this (section 5).
- Hosts must not list minors' harnesses in public directories.

### 2. Access: OAuth, with the UMA 2.0 grant for requesters

In MCP the person who approves access is the person using the client, reaching their own data. OHH's main case is different: a recruiter, platform or agent wants **someone else's** data, and the owner (or guardian) approves later, often from another device. OAuth's standard for that is **[UMA 2.0](https://docs.kantarainitiative.org/uma/wg/rec-oauth-uma-grant-2.0.html)** (User-Managed Access), so v0.3 uses it rather than inventing an approval protocol.

**Resource and authorization server.**

- **The protected resource is an OAuth protected resource.** It publishes [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728) Protected Resource Metadata naming its authorization server, which supports the UMA 2.0 grant and [UMA Federated Authorization](https://docs.kantarainitiative.org/uma/wg/rec-oauth-uma-federated-authz-2.0.html).
- **Each harness is its own resource.** The published harness points at it with a new top-level `access` block:

  ```json
  "access": {
    "resource": "https://harness.example.com/h/adnanlodhi",
    "resource_metadata": "https://harness.example.com/.well-known/oauth-protected-resource/h/adnanlodhi"
  }
  ```

  Each section is registered with the authorization server as a UMA resource set, owned by the harness owner. Because the resource is per harness and tokens are bound to it ([RFC 8707](https://www.rfc-editor.org/rfc/rfc8707)), a token issued for one person can't be used on another person on the same host.

**How a requester gets access.**

1. The requester calls the section's `href` without a token. The protected resource answers `401` with a UMA **permission ticket** for that section and its scopes.
2. The requester takes the ticket to the authorization server's token endpoint using the UMA grant. It **pushes its purpose as a claim**, with claim token format `https://openhiringharness.org/claims/purpose`:

   ```json
   {
     "purpose": "Evaluate fit for a 3-month data pipeline build for ClientCo",
     "requester_type": "platform"
   }
   ```

   `requester_policy.require_purpose` and `require_scopes` from v0.2 now mean: the authorization server refuses a request without this claim or without scopes.
3. If the owner's standing rules already allow it, the authorization server issues an access token (a UMA RPT) at once. Otherwise it answers `request_submitted`. It then asks the owner, plus the guardian for a minor, to approve, and the requester polls with the same ticket. This asynchronous step is UMA's, not OHH's.
4. Once approved, the requester gets a token scoped to those sections of that harness. A grant needing two approvals (student and guardian) is issued only when both have approved.

**The owner's own apps** (for example the owner's AI assistant reading their own harness) use the ordinary authorization code flow with PKCE, as MCP clients do. A host may expose the protected resource as an MCP server for these clients, with sections as resources; `docs/mcp-interface.md` is updated to say so. That surface is optional.

**Who the requester is.** A client's self-declared name is display text only. v0.3 uses **[Client ID Metadata Documents](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/)**, the direction MCP is taking: the requester's `client_id` is an HTTPS URL on its own domain, serving its metadata. The **verified domain** is the host of that URL, and it's what the owner sees and what the receipt records. This is still an IETF draft. If it changes before v0.3 is final, the spec follows it. Clients registered by other means (for example [RFC 7591](https://www.rfc-editor.org/rfc/rfc7591) dynamic registration) are allowed, but their domain is shown as **unverified**.

**Standing rules stay private.** The rules under which `permissioned` sections are granted without asking each time live in the owner's authorization server, not in the harness. v0.3 says only that they exist and that `private` sections always need explicit approval. Publishing rules or delegates in the harness waits for the agent entities proposal.

**Grants are time-limited.** `consent.max_standing_grant_days` caps how long a grant lasts. Access tokens are short-lived.

**Revocation.** The owner can always revoke a grant through their host. This is a requirement on hosts; how it's presented is up to them. Revocation must take effect within **5 minutes**. The protected resource meets that either by checking each token with [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662) introspection, or by issuing access tokens that live no longer than 5 minutes. Clients revoke their own tokens with [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009) at the endpoint in the authorization server's metadata. `consent.revocation` is removed from the harness, and so is the `harness://` scheme.

**Scope vocabulary.** v0.3 defines read scopes per section, with the prefix `ohh:`:

| Scope | Grants |
|---|---|
| `ohh:identity.read` | `identity` (when non-public) |
| `ohh:contact.read` | `identity.contact` |
| `ohh:offer.read` | `offer` (when non-public) |
| `ohh:rates.read` | `offer.rates` |
| `ohh:availability.read` | `availability.summary` and `availability.detail` |
| `ohh:proof.read` | `proof` |
| `ohh:reputation.read` | `reputation.redacted` |
| `ohh:reputation.full.read` | `reputation.full` |
| `ohh:career_fit.read` | `career_fit` |

**Actions are reserved, not defined.** `ohh:quote.request`, `ohh:hold.request` and `ohh:endorsement.submit` are reserved names. v0.3 defines no endpoints or payloads for them; that's later work. Implementers may add scopes under their own prefix.

### 3. Consent receipts become the record, not the mechanism

The OAuth grant is what enforces access. The consent receipt stays, as the human-readable record of what was granted:

- The authorization server (or the host) writes a receipt for every grant, refusal and revocation.
- Receipts are **never published**. `consent.log_location` and the `/.well-known/hiring-consent-log.json` path are removed. The owner reads receipts through the host.
- The receipt keeps its v0.2 fields and gains:
  - `grant_id`, linking it to the grant;
  - `outcome` (`granted`, `refused` or `revoked`);
  - `requester_domain` and `requester_domain_verified` (true only for Client ID Metadata Document clients);
  - `purpose`, copied from the pushed claim;
  - `sections`, `approved_by` (owner, guardian or standing rule) and `revoked_at`.
- The consent log gets a JSON Schema of its own, closing the v0.2 TODO.
- The top-level `consent_receipts` array, deprecated in v0.2, is removed.

### 4. Provenance on every claim

Every claim-bearing item gains a `provenance` object. That covers each skill, each reputation claim, each endorsement, each case study and each item in the new `career_fit` section.

```json
"provenance": {
  "source": "assessed",
  "observed_at": "2026-09-14",
  "issuer": { "name": "Guidebeam", "url": "https://guidebeam.com" },
  "method": "O*NET Interest Profiler Short Form",
  "evidence_url": "https://guidebeam.com/verify/..."
}
```

| `source` | Meaning | Example |
|---|---|---|
| `self_declared` | The owner said so | "Python: expert" typed by the owner |
| `assessed` | A named, validated instrument measured it | An interest profile from a published assessment |
| `first_party` | Structured data from the system that observed it | A course completion recorded by the school's system |
| `attested` | A named third party vouches for it | An employer's end-of-placement report |
| `inferred` | Derived by software, including AI, from other data | Skills an AI extracted from a CV |

Rules:

- `source` is required. `issuer` is required for `assessed`, `first_party` and `attested`. `method` is required for `assessed` and `inferred`.
- `self_declared` is the default when migrating v0.2 data, because nothing in v0.2 proves otherwise.
- Consumers must not present `inferred` claims as the owner's own statements.
- The spec says how to label provenance, never how to weight it. No scores.

**Relation to Guidebeam's evidence tiers** (informative, not normative): `self_declared` ≈ T0 owner statements, `assessed` ≈ T1, `first_party` ≈ T2, `inferred` ≈ T3. `attested` has no Guidebeam tier yet; it is the gap v0.4 fills with Verifiable Credentials.

### 5. Profile kinds

A new required policy block, `profile`, says what kind of harness this is. It has exactly two fields:

- `kind` (required): one of the values below;
- `minor` (boolean, default `false`): the person is under 18.

Names and everything else about the person stay in `identity`.

| `kind` | Who | Required beyond the core (checked on the resolved harness) |
|---|---|---|
| `independent` | Freelancers, contractors, consultants | `offer` with `services`; `offer.rates` (as in v0.2) |
| `job_seeker` | People looking for employment | `offer.roles` or `career_fit.target_occupations` |
| `employee` | People in a job who want a portable record | nothing extra |
| `student` | People in school or study | the student rules below |

The core required for every kind is:
- `version`, `entity_type`, `profile`, `identity`, `privacy`, `consent` and `requester_policy`;
- `access`, whenever any section is non-public.

`offer` and `availability` become optional except where the table requires them. Kind-specific requirements are checked by the resolved harness schema, because the fields they need may be non-public. The published schema checks only what the published file can show.

`entity_type` is added at the top level with one value, `individual`, defaulting to it. Agent values stay in the agent entities proposal.

**Student rules.** These apply when `profile.kind` is `student` or `profile.minor` is `true`:

- **No published file by default.** A student's harness is normally reachable only through the host. If a published file exists, every section in it, including `identity`, must be `permissioned` or `private`. Only the policy blocks are inline. The schema enforces this.
- **Not indexable.** `privacy.indexing.allow` must be `false`.
- **Guardian consent for minors.** When `profile.minor` is `true`, `consent.guardian_required` must be `true`. The authorization server then issues a grant only after both the student and a guardian approve (section 2, step 4). How a guardian is identified is open question 2.
- **Hosted, not self-hosted.** A student's harness is expected to live with a host such as a school or a service the school uses. The spec doesn't forbid self-hosting, but hosts must not list minors' harnesses in public directories.

### 6. Standard codes for skills and occupations

`Skill`, `offer.roles` and the new target occupations accept an optional `codes` array:

```json
"codes": [
  { "system": "esco", "code": "http://data.europa.eu/esco/skill/...", "label": "use spreadsheets software" },
  { "system": "onet-soc", "code": "15-2051.00", "label": "Data Scientists" },
  { "system": "anzsco", "code": "224115", "label": "Data Scientist" }
]
```

`system` is one of `onet-soc`, `esco`, `anzsco`, `osca`, `isco-08`, or an `x-`-prefixed custom value. Free-text names stay required, so a harness is still readable without codes.

### 7. Career fit (optional)

A new optional `career_fit` section, `permissioned` by default and never `public` for students:

- `interests`: RIASEC scores (`R`, `I`, `A`, `S`, `E`, `C`, each 0–100) with `provenance`, normally `assessed`.
- `work_values`: a list of named values with optional importance and `provenance`.
- `target_occupations`: coded occupations (section 6) the person is aiming for.

Scores carry the instrument in `provenance.method` so consumers know what was measured. The spec does not define how to interpret scores.

## Migration from v0.2

| v0.2 | v0.3 |
|---|---|
| `version: "0.2.0"` | `version: "0.3.0"`; add `entity_type: "individual"` and `profile: { "kind": "independent" }` |
| `identity`, `offer` (plain objects) | Wrapped in envelopes with `visibility: "public"`, so their content doesn't change |
| Non-public envelope with `data` | Move `data` to the protected resource; replace with `href` + `scopes_required` |
| `scopes_required` values such as `read:rates` | `ohh:` scopes per the table in section 2 |
| `consent.log_location`, top-level `consent_receipts` | Removed; receipts are kept by the host |
| `consent.revocation` | Removed; revocation is a host requirement and the authorization server's metadata (section 2) |
| — | Add `access` when any section is non-public |
| `consent.receipt_format` | Removed; the consent log schema defines the receipt |
| Skills, claims, endorsements, case studies | Add `provenance` with `source: "self_declared"` unless better evidence exists |
| `IssuerVerification` on endorsements | Replaced by `provenance` (`attested` + `issuer`); cryptographic proof arrives in v0.4 |
| Discovery (well-known path, DNS TXT, link rel) | Unchanged |

The repository ships `scripts/migrate-0.2-to-0.3.mjs`. It produces the published harness plus a separate file of protected sections, and it never writes non-public data into the published output.

## Security and privacy considerations

- **Caching.** The published harness may be cached by anyone; that's why it holds only public data. The protected resource must send `Cache-Control: no-store` for non-public sections. A section's `cache_ttl_minutes` tells the requester how long it may keep the data after reading it; it does not permit shared caches.
- **Token audience.** Each harness is its own resource and tokens are bound to it (RFC 8707), so a token for one person can't be used on another person, even on the same host.
- **Purpose limitation.** The purpose pushed as a claim is recorded in the receipt and shown to the owner. The spec cannot enforce how a requester uses data after release, and says so plainly.
- **Rate limits.** `privacy.rate_limits` applies to both surfaces; the protected resource counts per client.
- **Minors.** Covered by the student rules. Hosts serving minors must also follow their jurisdiction's child-privacy law; the spec points this out without restating it.

## Decided in this document

These are the author's calls, open to challenge in the comment period:

- OAuth with the **UMA 2.0 grant** for requesters (asynchronous owner approval, permission tickets, pushed purpose claims), plain authorization code + PKCE for the owner's own apps, and RFC 9728, 8707, 7662 and 7009 around it. Consent receipts are the record, not the access mechanism.
- **Client ID Metadata Documents** for verifying who a requester is; other registration methods allowed but shown as unverified.
- **One resource per harness**, so audience binding separates people on the same host. Harnesses are identified by URL, and a harness may have no published file.
- `identity` and `offer` become envelopes. `profile`, `access`, `privacy`, `consent` and `requester_policy` are always-public policy blocks.
- **Published and resolved schemas**, with kind-specific requirements checked on the resolved one.
- Standing rules and delegates stay private to the authorization server in v0.3.
- Action scopes are reserved names only. No action endpoints in v0.3.
- Revocation takes effect within 5 minutes, through introspection or short-lived tokens.
- The public consent log is removed entirely rather than protected.
- Five provenance sources, including `inferred`.
- `entity_type` is added now with only `individual`; agents are not in v0.3.
- Free-text names stay required alongside codes.

## Left to the implementer

- Choice of authorization server and how owners sign in to it.
- Consent-screen design, and how owners review and revoke grants.
- How standing rules are expressed inside the authorization server.
- Storage of protected sections and receipts.
- Whether to expose an MCP surface.
- How a guardian is identified and verified (subject to open question 2).

## Open questions

1. **Should students be in v0.3 at all?** Including them makes OHH useful to schools and to Guidebeam, but a public standard for minors' records raises the stakes. The alternative is to ship `independent`, `job_seeker` and `employee` in v0.3 and add `student` in v0.3.1 once the guardian model is settled.
2. **Guardian identity.** Should the spec define how a guardian is linked to a student (for example a claim issued by the school), or leave it entirely to hosts?
3. **Comment period.** GOVERNANCE.md requires 14 days for breaking changes. Should this proposal open for comment publicly now, or after a private review?
